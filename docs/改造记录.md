# 寻味 Xunwei · 改造记录

> 城市探店点评与优惠券秒杀平台（Java 后端为主 + Vue3 前端）。
> 配套文件：`README.md`（快速上手）、`db/init.sql` + `db/seed-seckill.sql`（建库与演示数据）。

本项目在开源教程项目（黑马点评）基础上改造而成。本文档记录**相对原实现改了什么、为什么这么改**。

---

## 一、为什么要改造

原实现有三个问题：

| 问题 | 具体是什么 |
| --- | --- |
| git 历史是别人的 | 原仓库的 remote 指向他人的 gitee 仓库，34 个 commit 作者都不是我，首次提交是 2021-12-22 的 `Initial commit` |
| 技术栈过旧 | Spring Boot 2.3.12 + Java 8 |
| 代码里压着大量历史版本 | 50 个文件带原作者署名；核心的 `VoucherOrderServiceImpl` 411 行里有 225 行是注释掉的历史实现（阻塞队列版、两版自研分布式锁） |

改造的目标是升级技术栈、重写前端，并把原实现里的真实缺陷挖出来修掉。

## 三、修复的 13 个真实缺陷

> 全部是在改造过程中**实际跑出来的**，不是"看起来可能有问题"。每个都写了：现象 → 根因 → 修法。

### P1 `@Transactional` 因类内自调用完全失效 ⭐

- **现象**：`VoucherOrderServiceImpl.createVoucherOrder()` 上标了 `@Transactional`，看起来事务没问题。
- **根因**：Spring 事务是 AOP 代理实现的，**只有从外部经过代理调用才会开事务**。这个方法的两条调用路径
  都是类内自调用：同步路径 `return createVoucherOrder(voucherId);`，异步路径从内部类里直接调。
  走的是原始对象，代理被绕过，注解形同虚设 → **"扣库存"和"建订单"根本不在一个事务里**。
- **修法**：把落库逻辑拆到独立的 Bean `VoucherOrderPersister`，通过注入的代理调用。
- **值得记住的点**：这是"为什么要分层/拆 Bean"最实在的理由——不是为了代码好看，是为了注解能生效。
  同一个坑还有几种形态：`@Async` 自调用失效、`@Cacheable` 自调用失效，原理一样。

### P2 消费组从未创建，启动就无限刷错误

- **现象**：应用一启动就疯狂输出
  `NOGROUP No such key 'stream.orders' or consumer group 'g1' in XREADGROUP with GROUP option`，每秒几十条。
- **根因**：`@PostConstruct` 只起了消费线程，从没执行过 `XGROUP CREATE`。消费线程是 `while(true)` 的，
  所以这个错误会一直刷下去。
- **修法**：启动时 `XGROUP CREATE stream.orders g1 $ MKSTREAM`。
  必须用底层连接才能带 `MKSTREAM`——否则 Stream 还不存在时建组会失败，组永远建不出来。

### P3 `XACK` 把流名写成了组名，消息永远确认不掉

- **现象**：消息被反复处理。
- **根因**：代码写的是 `acknowledge("s1", "g1", recordId)` —— 第一个参数应该是**流名**，
  而 `s1` 是消费组名，真正的流叫 `stream.orders`。于是 XACK 作用在一个不存在的 key 上，
  消息永远留在 pending 列表里，每次回收都被重放。
- **修法**：抽成常量 `SECKILL_STREAM`，两处都改对。
- **危险在哪**：这类"参数顺序对但语义错"的 bug 不会报错，只会让消息重复消费；
  如果业务没有幂等保护，就是重复下单。

### P4 异常分支形成忙循环，刷爆日志 + 吃满一个 CPU 核

- **现象**：配合 P2 一起出现，日志文件几秒涨几 MB。
- **根因**：`catch` 里直接调 `handlePendingList()`，而它内部也是 `while(true)` 且会撞同一个异常 →
  "异常 → 进 pending 循环 → 再异常"的忙循环。
- **修法**：读失败退避 2 秒再试；并且区分"该不该重试"——
  业务失败（库存真没了、确实重复下单）要 ACK 掉，不然只是无限重放；系统失败（DB 连不上）才不 ACK、留 pending 等重试。

### P5 秒杀时间窗校验被弄丢了

- **现象**：**已结束的秒杀券照样能下单**。
- **根因**：原实现早期版本在 Java 里校验 `beginTime` / `endTime`，后来换成 Lua 方案时把这段删了，
  而 Lua 脚本只管库存和一人一单，不管时间。
- **修法**：补回时间窗校验，返回 `SECKILL_NOT_START` / `SECKILL_ENDED`。
- **怎么复现**：`db/seed-seckill.sql` 特意造了三种时间窗的券（进行中 id=2 / 未开始 id=3 / 已结束 id=4），
  拿 id=4 打一次就知道。

### P6 雪花 ID 超过 JS 精度范围，前端拿到的订单号是错的 ⭐

- **现象**：秒杀下单后，前端拿返回的订单号去查结果，**永远查不到**，界面卡在"订单处理中"。
- **根因**：订单号是雪花 ID，形如 `643388832540000561`（60 位整数），
  而 JavaScript 的 `Number` 只能精确表示到 2^53 ≈ 9.0e15，比它小两个数量级。JSON 里的数字到了前端被**静默改写**：

  ```
  后端真实值              643388832540000561
  前端 JSON.parse 之后     643388832540000500   ← 末两位被四舍五入
  ```

  而且**不报任何错**：数字看起来正常，只是末尾不一样。
- **修法**：所有可能超过 2^53 的 Long 一律按字符串序列化
  （实体字段加 `@JsonSerialize(using = ToStringSerializer.class)`；秒杀接口的返回值直接改成 `Result<String>`）。
- **为什么原实现没暴露**：因为原项目**根本没有"查询订单结果"这个接口**，那个 id 从来没被回传过，
  前端只显示一句"下单成功"就结束了。是补上轮询接口之后它才现形。
  → 这本身就是个教训：**接口设计不完整会把 bug 藏起来**。
- **踩坑细节**：第一版只在实体字段上加了注解，没管秒杀接口那个"裸 Long"出口，
  结果还是错的。所以加了 `OrderIdSerializationTest` 把规则钉住——靠注释和记忆守不住。

### P7 `tb_user_info` 主键用了 `IdType.AUTO`，但这一列没有自增

- **现象**：编辑资料第一次保存就失败（对还没有资料行的用户）。
- **根因**：`user_id` 是外键（指向 `tb_user.id`），DDL 里没有 `AUTO_INCREMENT`；
  而实体标了 `IdType.AUTO`，MyBatis-Plus 插入时会省略这一列、指望数据库生成 →
  报 `Field 'user_id' doesn't have a default value`。
- **修法**：改成 `IdType.INPUT`。

### P8 分类图标的路径本来就是错的

- **现象**：首页 10 个分类图标全是灰块。
- **根因**：数据库里 `tb_shop_type.icon` 的值是 `/types/ms.png`，但资源文件实际在 `imgs/types/` 下。
  翻过原 nginx 配置，**没有对应的 alias**——也就是说这个 404 在原静态站里就存在，是原项目自带的数据错误。
- **修法**：资源复制进前端 `public/imgs/`，数据改成 `/imgs/types/xxx.png`。
- **顺带修的一个坑**：本来在 vite.config 里写了 `/imgs` 代理到后端，
  结果请求被转发到后端、撞上登录拦截器返回 **401**，页面上同样是灰块。
  图片在前端本地就不该代理——这个是把配置删掉才对的。

### P9 同一套表里金额单位不统一

- **现象**：商铺人均显示成 `¥0.80`，应该是 `¥80`。
- **根因**：`tb_shop.avg_price` 存的是**元**（80 = 80 元），
  而 `tb_voucher.pay_value` / `actual_value` 存的是**分**（4750 = 47.5 元）。
  一开始统一按"分"处理，除 100 就错了。
- **修法**：前端分开两个格式化函数并注明来源；后端统一单位是更彻底的做法（记在技术债里）。

### P10 `Result.isSuccess()` 被 Jackson 当成属性序列化出去

- **现象**：响应里多出一个 `success` 字段，和 `code` 表达同一件事。
- **根因**：Jackson 会把 `isXxx()` 当作名为 `xxx` 的属性。
- **修法**：加 `@JsonIgnore`。两处真相迟早不一致，干脆不输出。

### P11 `logout` 是个空桩

- **现象**：原项目里 `POST /user/logout` 直接返回"功能未完成"，**前端点登出其实没登出**。
- **修法**：实现之——删掉 Redis 里的登录态，令牌立刻作废。
  这也顺带说明了一件事：**登录态放 Redis 而不是 Session，换来的是"服务端可以主动吊销令牌"**，
  这是纯 JWT 做不到的。

### P12 验证码被改成了字母数字混合

- **现象**：`RandomUtil.randomString(6)` 会生成字母，与"6 位数字短信验证码"的约定不符。
- **修法**：改回 `randomNumbers(6)`。
- **顺手做的一件事**：**验证码一旦用过就删掉**。原实现里验证码在有效期内可以反复用。

### P13 券的使用规则里 `\n` 是转义残留

- **现象**：使用规则显示成 `全场通用\n无需预约\n...`。
- **根因**：原始数据是 MySQL 5.6 导出的，换行被写成了转义序列（两个字符）。
- **修法**：数据清洗 + `init.sql` 源头改用 `CONCAT(..., CHAR(10), ...)` 生成真正的换行。

## 四、相对原项目新增的东西

| 新增 | 为什么必须有 |
| --- | --- |
| **`GET /voucher-order/{orderId}` 查询下单结果** | 下单是异步的，没有这个接口前端无从知道订单成没成，只能乐观显示"下单成功"。**P6 就是被它逼出来的** |
| **`GET /voucher-order/of/me` 我的订单** | 一次 JOIN 取齐券名与商铺名，避免列表页 N+1 次请求 |
| **`GET /voucher/{id}` 按 id 查券** | 秒杀页只有 voucherId、没有 shopId，原来只能按商铺查 |
| **`PUT /user/info` 保存资料** | 编辑资料页要能保存；用户 id 从登录态取而不是前端传（防水平越权） |
| **`SeckillStockWarmer` 启动预热秒杀库存** | 秒杀脚本第一步是 `GET seckill:stock:{id}`，key 不存在时 Lua 会直接报错。直接往库里塞活动数据时没人写 Redis |
| **`ShopGeoWarmer` 启动预热商铺 GEO 数据** | 附近商铺依赖 Redis GEO，"这份数据只在 Redis 里、库里没有镜像"。原实现把这段写在测试类里，靠人记得手工跑 |
| **`uk_user_voucher` 唯一索引** | 一人一单的**正确性保证**（下面第五节详述） |
| **6 个带断言的测试** | 原实现那 3 个测试文件没有一条断言，还带 100 万次循环和改 Redis 的副作用 |

## 五、这个项目真正的技术含量在哪

一句话：**三道防线各司其职**。

```
请求 ──▶ ① Redis Lua 原子预检 ──▶ ② 消息队列异步削峰 ──▶ ③ 数据库事务 + 唯一索引
            判库存 / 判一人一单         Stream + 单线程消费        建单 + 扣库存 + 兜底
```

| 防线 | 职责 | 少了它会怎样 |
| --- | --- | --- |
| ① Redis Lua | **性能**：挡住 99% 的无效请求，让它们根本到不了数据库 | 数据库被瞬时流量打垮 |
| ② Redis Stream | **削峰**：把下单变成异步，接口立刻返回 | 接口响应时间被数据库事务绑住 |
| ③ 事务 + 唯一索引 + 条件 UPDATE | **正确性**：与并发、重试、消息重放无关地保证不超卖、不重复 | 只靠 ① 是不安全的（Redis 会丢数据、消息会重放） |

**为什么 Lua 必须原子**：判库存 → 扣库存 → 记用户 → 发消息，这四步之间被任何请求插进来就会超卖或重复下单。

**为什么"一人一单"最终必须落数据库唯一索引**：
Redis 的 `SISMEMBER` 预检挡的是"同一用户同一瞬间的重复请求"，
但**消息会被重放**（pending 列表恢复）、**进程会崩**、**人也会直接去库里改数据**——这些 Redis 都拦不住。
唯一索引是最后一道、也是唯一一道不依赖外部状态与时序的防线。

**为什么扣库存必须用条件 UPDATE**：
`SET stock = stock - 1 WHERE voucher_id = ? AND stock > 0`
把"判断有没有库存"和"减库存"合成一条语句，靠 InnoDB 行锁保证原子性。
拆成"先 SELECT 判断、再 UPDATE"两步，两个并发请求会同时读到 `stock=1` 然后各扣一次 → 超卖。

**为什么落单顺序是"先插订单再扣库存"**：
重复下单会在第一步就被唯一索引拒掉，**库存完全没被动过**，连回滚都不需要。
反过来先扣库存，重复请求会白白扣掉一张再靠回滚补回来——徒增锁竞争和回滚开销。

## 六、并发正确性数字

测试类：`SeckillIntegrationTest`

| 场景 | 结果 |
| --- | --- |
| **100 个用户并发抢 10 份库存** | Redis 预检恰好放行 10 个、其余 90 个被拒；**落库恰好 10 张订单**；数据库库存归零且不为负；Redis 库存同步归零 |
| **同一用户并发提交 50 次** | 只拿到 **1 次**资格；数据库 **1 张**订单；库存只扣 1 |
| 接口耗时 | 100 个请求 **206 ms**（≈ 485 请求/秒，含本地 Redis + MySQL，单机） |

**加锁与防超卖的两条纪律**：

- 并发测试必须用 `CountDownLatch` 造"同一瞬间起跑"的真并发。
  普通 `for` 循环里前一个请求早就返回了，线程之间根本不重叠——**那样一个错的实现也能跑通**。
- 断言要"精确等于"而不是"大约"。余额是整数分累加出来的十进制数，并发正确时结果必须一位不差。

## 七、前端：重写了什么，以及只有真跑起来才能发现的两个问题

12 个路由页面，**Vue3 + Vite 6 + TypeScript + Element Plus + Pinia**：

| 页面 | 说明 |
| --- | --- |
| `/login` | 手机号 + 验证码登录（60 秒倒计时、登录后回到原目标页） |
| `/` | 首页：分类导航 + 附近好店（GEO 距离排序）+ 热门探店 |
| `/shops` | 商铺列表：分类筛选 + 名称搜索 + 分页 |
| `/shops/:id` | 商铺详情：图片轮播 + 秒杀券（带倒计时）+ 普通券 |
| `/seckill/:voucherId` | **秒杀页**：抢购 + 轮询确认订单结果（见下） |
| `/orders` | 我的订单 |
| `/blogs` | 探店笔记：热门 / 我关注的（滚动分页） |
| `/blogs/:id` | 笔记详情：点赞 + 点赞的人 |
| `/blogs/edit` | 发布/编辑笔记：远程搜索选商铺 + 多图上传 |
| `/me` | 个人主页：资料 + 签到（Bitmap）+ 我的笔记 |
| `/me/edit` | 编辑资料 |
| `/users/:id` | 他人主页：关注 / 取关 + 共同关注 |

**秒杀页是整个前端最值得说的地方**：它必须正确处理"异步下单"这个语义。

抢购接口返回成功 ≠ 订单已创建。接口返回的 orderId 只是"排队凭据"。
所以前端拿到 orderId 后要**轮询**查询结果，并且要能区分两种"没成功"：

- 后端返回 `44005`（订单处理中）→ **不是错误，继续轮询**
- 其它错误码（库存不足 / 已在别处下过单）→ 立刻停止，如实提示

原实现没有结果查询接口，前端只能乐观地提示"下单成功"——订单万一落库失败，用户永远等不到那张券。

**只有真跑起来才能发现的两个问题**：

1. **登录页的顶部还显示着"登录/注册"按钮**，页面上出现两个同名按钮。这是端到端验证时
   （按钮定位不再唯一）才暴露的。
2. **"附近好店"对不在杭州的人是空的**。后端按"距我 5 公里以内"查，而演示数据全在杭州；
   实测浏览器真实定位在安徽，距杭州约 250 公里 → 空列表。
   处理方式是**如实说明 + 给退路**：落空时改为展示该分类的全部商铺，
   标题变成"这些店都在杭州"，并注明"你的位置周边 5 公里内没有商户"。
   ——不是假装有附近，也不是把半径调到失真。

## 八、已知技术债

| 技术债 | 影响 | 该怎么修 |
| --- | --- | --- |
| 金额单位不统一（`avg_price` 元 vs `pay_value` 分） | 前端要写两套格式化，容易再错 | 后端统一成"分"，或统一成"元"并全局约定 |
| 倒计时以浏览器时间为准 | 用户把系统时间往前调就能"提前开抢" | 服务端下发时间偏移量，前端按偏移计算 |
| 秒杀时间窗只在请求时校验 | 消息排队期间跨过结束时间仍会落单 | 落库前再校验一次，或把窗口也放进 Redis 由 Lua 判断 |
| 库存键丢失时按 DB 值重建，可能把已承诺的名额再发一次 | 极端情况下请求会多进来一批 | 不会真超卖（数据库条件 UPDATE 兜底），但会多失败一些请求；彻底解法是库存与订单对账 |
| 单机单消费者 | 消费线程是单点 | 多消费者靠唯一索引保证正确性，但这个方案还没实测过 |
| 商铺/笔记列表分页不返回 total | 前端只能按"本页满不满"猜有没有下一页 | 后端返回 total，前端改真分页 |
| Element Plus 全量引入，首屏 JS 1.12MB（gzip 371KB） | 首屏偏重 | `unplugin-vue-components` 按需引入，预计能减 60% 左右 |
| 表名带 `tb_` 前缀 | 命名不够简洁 | 改动面大（实体/SQL/前端都要动），暂留 |
| 没有管理后台 | 新建秒杀券只能打接口 | 本项目定位是后端，前端只做用户侧；接口已留好 |

## 九、怎么跑起来

```bash
# 1) Redis（本机原生；带 AOF 因为秒杀库存是短期真相）
redis-server.exe redis.conf --appendonly yes          # 默认 127.0.0.1:6379

# 2) 数据库（首次）
mysql -uroot -p -e "CREATE DATABASE xunwei DEFAULT CHARACTER SET utf8mb4;"
mysql -uroot -p xunwei < db/init.sql          # 表结构 + 基础数据
mysql -uroot -p xunwei < db/seed-seckill.sql  # 秒杀活动数据（可重复跑，用相对时间）
mysql -uroot -p xunwei < db/fix-escape-newlines.sql   # 一次性：清洗历史转义脏值

# 3) 本地配置（含口令，已 gitignore）
cp src/main/resources/application-local.yml.example src/main/resources/application-local.yml

# 4) 后端
mvn spring-boot:run                            # http://127.0.0.1:8081

# 5) 前端
cd frontend && npm install && npm run dev       # http://localhost:5173
```
